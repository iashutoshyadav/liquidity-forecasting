# Data provenance statement

## Data modes

| Mode | How to select | What is real | What is synthetic |
|---|---|---|---|
| **hybrid** (default) | `--data-mode hybrid` or omit | FX rates (`currency_rate`); calibration of customer payment delays | everything else |
| **synthetic** | `--data-mode synthetic` | nothing | everything, including GBM FX rates and assumed delays |

In both modes, the following are generated by `liqfc.generators` with seed `20261022`: entities,
bank accounts, ledger, receivables, payables, forecast items, statements, scenarios and anomalies.
No public dataset contains a corporate group's treasury records, so these parts must be synthetic.
That matches the problem statement's guidance.

## External datasets used (hybrid mode)

The pipeline never downloads anything. It reads small **pinned** files in `data/external/`, built
once by `scripts/prepare_external_data.py` from the raw Kaggle downloads. `data/external/SOURCES.json`
holds the machine-readable record, including raw and output SHA-256 checksums. The checksums of the
files actually used are also stored in every run's `manifest.json` and included in the config hash.

### 1. Real FX rates → `currency_rate`

| Item | Value |
|---|---|
| Source URL | https://www.kaggle.com/datasets/asaniczka/forex-exchange-rate-since-2004-updated-daily |
| Dataset / version | `asaniczka/forex-exchange-rate-since-2004-updated-daily`, **version 1091** (pinned; version 1092 was not yet downloadable) |
| Retrieved | 2026-10-27 |
| Licence | **ODC Attribution License (ODC-By)**: reuse and redistribution permitted with attribution |
| Attribution | "Forex Exchange Rates Since 2004" by asaniczka, Kaggle |
| Raw file | `daily_forex_rates.csv` (508,355 rows, EUR base, 176 currencies) |
| Transformations | Kept USD, GBP, INR and JPY rows for project business days 2025-12-31 to 2026-06-30. Converted from "units per EUR" to "USD per 1 unit": EUR = USD/EUR; X = (USD/EUR) ÷ (X/EUR). Exact Decimal division, 8 dp, ROUND_HALF_EVEN |
| Fields / rows discarded | `currency_name`; 172 other currencies; weekend and holiday rows; dates outside the window |
| Output | `data/external/fx_rates_kaggle_v1091.csv` (508 rows = 127 business days × 4 currencies) |
| Effect | Configured FX shocks and GBM parameters are not used in this mode. Real moves already contain market shocks. Stress-scenario FX shocks still apply on top. |
| Caveat | The Kaggle page does not name the upstream rate source (central bank or market feed). The rates are used as realistic market levels, not as official fixings. |

### 2. Payment-delay calibration → receivable generation

| Item | Value |
|---|---|
| Source URL | https://www.kaggle.com/datasets/sonalisingh1411/accounts-receivable-and-payment-delay-analysis |
| Dataset / version | `sonalisingh1411/accounts-receivable-and-payment-delay-analysis`, version 1 |
| Retrieved | 2026-10-27 |
| Licence | **Apache License 2.0** |
| Attribution | "Accounts Receivable & Payment Delay Analysis" by Sonali Singh, Kaggle |
| Raw file | `Dataset.csv` (45,839 anonymised B2B invoices, 2014–2016) |
| Fields used | `Customer_Name` (anonymised code), `Days_Overdue_Delay` |
| Fields discarded | All other 27 columns (amounts, regions, cities, zip codes, dates, payment methods, flags) |
| Transformations | Customers with ≥ 20 invoices are segmented by median delay (A ≤ 2 days, B 3–10 days, C > 10 days). For each segment: trim the 1%/99% tails, set shift = floor(p05), and fit a method-of-moments gamma to (delay − shift) |
| Output | `data/external/ar_delay_calibration.json`: **aggregate statistics only, no rows redistributed** |
| Result | Class A: shift −4, shape 1.089, scale 4.429 (≈ 34% of invoices paid early). Class B: shift −2, shape 0.387, scale 18.935. Class mix A/B from invoice shares (92.3% / 7.7%), scaled to 90% |
| Not calibrated | Class C and write-off rates. The data contains no very late or unpaid invoices, so C (configured 10%) and write-offs remain **documented stress assumptions** |

## External datasets evaluated and rejected

| Dataset | Licence | Why rejected |
|---|---|---|
| `thuandao/bank-transactions-dataset-for-fraud-detection` | Apache 2.0 | Balances do not reconcile to transactions (0 of 49,505); retail card/ATM domain; one currency; IP addresses and demographic fields |
| `fedesoriano/company-bankruptcy-prediction` | "Data files © Original Authors" (not open) | Licence does not grant redistribution; annual normalised financial ratios with no IDs, dates or transactions |
| `polystash/public-holidays-by-country-and-region-2026-2028` | CC BY 3.0 | **Suitable, deferred.** Good coverage for 6 of 7 countries (India marked partial). Using it needs per-currency business calendars (code change); the project keeps one global calendar for now |
| `fridrichmrtn/public-holidays` | CC BY-SA 3.0 | Backup only. Share-alike obligation; missing US Juneteenth; regional days mixed into national codes; incomplete India |

## Other statements

* **No personal data.** Customers and suppliers are codes (`CUST-00042`, `SUPP-00007`). Payroll is an aggregate outflow to "EMPLOYEES". Company and bank names are clearly artificial (`LFX Synthetic Entity 001 (US)`, `Synthetic Bank Alpha`).
* **Redistribution.** Generated data can be redistributed with the code. The pinned FX extract is redistributed under ODC-By with the attribution above. The calibration file contains only derived statistics.
* **Derived values.** All balances, statuses, positions, forecasts, variances and metrics are computed from source records by the rules in `business_rules.md`.
* **Regenerating the pinned files.** Download the raw files with `kagglehub`, then run `python scripts/prepare_external_data.py --fx-csv <daily_forex_rates.csv> --ar-csv <Dataset.csv>`. `tests/test_external_data.py` checks the outputs against the checksums in `SOURCES.json`.
